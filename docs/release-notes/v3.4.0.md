## v3.4.0

### Changes

- **The escalation guard, on by default.** An operator grants and revokes only the permissions they hold in effect — laravel-access-control's `effectivePermissions()`, implied permissions included, restrictions and conditions applied. Cells outside that set are switched off with a tooltip; every write path checks it on the server: a cell's click, a subject's click, **Save permissions**, and `PermissionSelector`'s validation and dehydration. An operator holding the super-admin role is not narrowed. `->grantableBy(fn (User $operator) => [...])` replaces the set; `->preventEscalation(false)` switches the guard off.
- **The self-editing guard, on by default.** An operator does not change the permissions of a role they hold, nor their own direct permissions; the column and the editor say so. `->preventSelfEditing(false)` switches it off.

See [UPGRADING](../../UPGRADING.md#from-33-to-34).

### Features

- `->matrixComponent(MyMatrix::class)`: the access control page draws your subclass of `Livewire\RolePermissionMatrix`, and so does `PermissionMatrix::make()` without a component.
- `PermissionEditor::make()->showDirectGrants(false)`: for an application that grants through roles only, a user's editor hides the always-empty *Granted* column and shows what the roles grant and what is in effect.
- A read-only `PermissionEditor` (disabled, or on a view page) takes an account that does not implement `HasEditablePermissions`, as long as it is `AuthControllable`.

### Fixes

- A deferred **Save permissions** discards — with a notification naming the role and the reason — the staged changes it may not make (no longer authorised, the role gone), instead of keeping them staged with Save forever enabled; a save left with nothing to write no longer reports one.
- README: `PermissionEditor::ability()` with a closure picks the ability, it does not decide.
